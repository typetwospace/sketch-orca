# orca-cli

The Rust program, sketch-orca-rs: sketch-orca's commands, intake, presets stage, model stage, info answer, placement, parity knobs, declines and crash result.

From 0.3.0 (2026-11-11) it does everything `cli/run.cpp` does up to the front-objects boundary: the job, the presets, the model, an info job's answer, and a layers or slice job's placement. It declines what comes after (slicing), and a job that orients its objects.

The command line of the Rust translation: the program `sketch-orca-rs`, a separate program from the C++ `sketch-orca` of `cli/`, under the same licence. It is to run the protocol's commands (`version`, `config-def`, `run`) with the intake the C++ front end has, decline a job it cannot do yet before it writes any output (result code `not-ported`, exit -8, with a list of what is missing), and on a crash write the `internal-error` result and exit with -1.

What it answers so far:

- `help`, `--help`, `-h`: `cli/main.cpp`'s usage text on stdout, exit 0. No command: the usage on stderr after `sketch-orca: no command`, exit -2; an unknown command, an option a command does not take, a missing or repeated option or a missing value: the same message `cli/main.cpp` gives, the usage, exit -2.
- `version` (and `--version`): the C++ program's `version.json` line (`engine`, `engineVersion` from the workspace's version, `orcaVersion` 2.4.2, `orcaTag` v2.4.2, `orcaCommit` 8500fcdccaa10b5099ac20d252af3a7c560046f1), plus `implementation: "rust"` (`src/version.rs`).
- `config-def --out <file>`: the same file as the C++ program's, byte for byte (`parity/goldens/front/config-def.json`, with the engine version of the build): every setting of orca-config's definitions but SLA's, `coNone`'s and the obsolete keys, then the obsolete keys (`src/config_def.rs`). It is written as `cli/common.cpp`'s `write_file_atomic` writes it (`<file>.tmp`, then a rename; `src/files.rs`), with the same messages and exit -13 when it cannot be.
- `run --job <file> --out <file> [--progress <file>]`: its command line is checked as `cli/main.cpp` checks it, and a command line it does not take still gets an `invalid-params` result at `--out` when one can be written there. The run follows `cli/run.cpp`'s `run_job` and `run` as far as the front-objects boundary: the model stage, an info job's answer, and a layers or slice job's placement. The job is read and checked as `cli/job.cpp` reads it, in the same order and with the same messages (`src/job.rs`); the run's files (the job, every absolute path it names, the result, the progress file and the outputs with the files they are written through) are told apart as the C++ tells them apart (`src/result.rs`, `src/paths.rs`: Boost.Filesystem's `is_absolute`, and two names of one file on Windows); the result and the progress file are written as the C++ writes them (`src/result.rs`). Then come the presets stage, the model stage, the info answer and the placement, below. Every command line and job the C++ refuses up to there gets the same result, exit code, warnings and progress file; the corpus holds the C++ result of each such refusal up to the presets stage (`parity/goldens/front/intake/`, `tests/intake.rs`) but the thumbnails' internal error and some forms of `setting-invalid` (`src/presets.rs`), `tests/info.rs` holds the model stage's and `tests/place.rs` the placement's. A refusal the C++ makes later, from slicing on, comes from a step that is not ported, so such a job is declined instead.
- The presets stage (`src/run.rs`, `src/presets.rs`, on Orca's configuration in `src/config.rs`), as `cli/run.cpp` and `cli/presets.cpp` do it, step for step: the progress line `presets` (3); the resources folder must have a profiles folder (`environment`), and the work folder and its `orca-data` folder are made (`output-failed`), the work folder being Orca's temporary folder from then on (`set_temporary_dir`, where the 3MF reader makes its backup folder); the machine, process and filament presets are read (`file-not-found`; `preset-invalid` for a file that is not JSON or not an object, of the wrong type, from elsewhere or with a value Orca cannot read; `not-fdm`; a value of no form Orca reads is skipped with `preset-value-skipped`, an enum value it does not know substituted with `setting-substituted`), checked against each other (`process-not-compatible`; a filament that does not match is a warning) and merged, the job's overrides applied (`setting-invalid` for a key Orca does not have or a value it cannot read) and the whole checked as Orca checks it (`config-invalid`, the flushing volumes' inputs included), with the C++ warnings in the same order. A preset that has no `compatible_printers` or `compatible_prints` list but a condition has it worked out by orca-placeholder as `Preset.cpp` (lines 771-845) works it out (2026-11-07): the printer's condition against the printer preset's own settings with the override `printer_preset` and `num_extruders`, the process's against the process preset's; a condition that does not parse counts as compatible, and its error goes where Orca sends it (the printer's to stderr as a `[warning]` line at `SKETCH_ORCA_LOG_LEVEL` 2 or more, the process's to stdout). One the parser does not take (`Unsupported`) is declined there, in the presets stage, naming `preset-conditions` first and then the job's own families. The merged configuration is the C++ one key for key, `printer_model_id`, `is_bbl_printer`, `curr_bed_type` and the flushing volumes (`flush_volumes_matrix`, from FlushVolCalculator and its predictors, `resources/flush`) included; `src/presets.rs`'s tests compare the flushing volumes, the flush multiplier, the plate and the filament colours with the configuration block of every golden G-code (`SKETCH_ORCA_GOLDENS_DEEP=<work>/parity`), and the oracle's `front-objects` dumps hold the whole configuration from oracle patch 0006 on (`parity/SOP1.md`, CONF `run`).
- The model stage (`src/run.rs`, `src/model.rs`), as `cli/run.cpp` does it (2026-11-11): the progress line `model` (8); the model must be a file (`file-not-found`); its path is made preferred (`\` on Windows, as Orca's readers name an object after the text behind the last native separator) and orca-model's `read_from_file` reads it with `LoadModel | AddDefaultInstances`. A reader's error is `model-unreadable`, "cannot read the model <path>: <the reader's text>"; so is the CR box, an ASCII STL whose `solid` line passes 255 bytes, where the C++ engine dies (`parity/CORPUS.md`, "An engine fault"). Each object's and part's settings but the filament it prints with (`extruder`) are dropped, as are its height ranges and layer heights, for the job's presets decide every setting, and each object is put on the bed. Then each object the job lists must be one of the model's (`job-invalid`), and for a layers or slice job, or a job that orients its objects, each part Orca prints must enclose a volume (`model-unreadable`, naming the object: fewer than four triangles, flat, or an object of modifiers only). A job that orients its objects gets the progress line `orient` (10) and is declined there, naming `orient`, as orientation is not ported. A file that needs a reader orca-model has not translated would be declined naming `model-load`; a job's model is a .3mf, .stl or .obj file, so no job reaches that.
- The info answer (`src/info.rs`): an info job is answered whole, as `info_json` of `cli/run.cpp` answers it: each object's index, name, instances, triangles (its parts', modifiers left out) and box on the bed; the bed (printable area and height, the excluded area when it has three points or more, the bed type); the printer preset, its model and the model's id, the process and filament presets, the nozzle count and the print sequence; lengths rounded to the micrometre. The run ends there, as the C++ run does.
- The placement (`src/place.rs`), as `cli/run.cpp` does it for a layers or slice job (2026-11-11), on a copy of the presets' configuration: each object the job lists gets its overrides and height ranges (`setting-invalid` for a printer, filament or whole-plate setting, a setting a height range does not take, a layer height not above 0 or a filament past the job's, naming the object); the job's custom G-code per layer becomes Orca's custom G-code of plate 1 (`custom-gcode-invalid`, and `unsupported` with print_sequence "by object"); the prime tower, when Orca prints one, is placed where the job sets it (`config-invalid` when it is not all on the printable area, off the excluded areas) or in the GUI's default corner, moved to the nearest place that fits (`arrange-failed` when none does), and stands as a fixed item for the arrange; a job that arranges gets the progress line `arrange` (12) and every instance arranged onto plate 1 as the stock command line arranges them, never rotated (`temperature-difference` for filaments far apart in temperature, `arrange-failed` for an object that does not fit); then the build volume check (`not-printable` for a printable object partly or wholly outside the printable volume, exit -50 when nothing is inside and -52 otherwise, and `empty-plate` when every object is marked not printable and none is inside). That is the front-objects boundary: with `SKETCH_ORCA_ORACLE_DUMP` set, the placed objects are dumped there, then the job is declined.
- The parity knobs (`src/oracle.rs`), for parity work only: the program reads the oracle's knobs as the oracle reads them (`parity/oracle/README.md`, oracle patches 0001 to 0006), so a run under the same knobs can be held to the oracle's byte for byte. A knob the oracle cannot read stops the program first: `sketch-orca-oracle: <what is wrong>` on stderr and exit 78, nothing written, in the oracle's order (`SKETCH_ORCA_ORACLE_FMA3`, `_THREADS`, then `_TIME`, `_SEED` and `_DUMP`). `SKETCH_ORCA_ORACLE_FMA3=0` turns the static UCRT's FMA3 paths off first of all (Windows x64 only; elsewhere it is refused, as the oracle refuses it); `SKETCH_ORCA_ORACLE_THREADS=P` runs the program in an arena of concurrency P on one thread (orca-tbb's serial arena); `_TIME` and `_SEED` are checked and reported only, since nothing up to the boundary reads the clock or a seeded generator (a 3MF's backup folder in the work folder is still named by the real time); `SKETCH_ORCA_ORACLE_DUMP=<folder>` writes `front-objects-<n>.sop1` there at the boundary, every record of oracle patches 0005 and 0006 (`parity/SOP1.md`) as `OracleDump.cpp` writes it, its RUN record reporting the knobs, the arena's concurrency, the thread limit and the CRT's FMA3 state. With no knob set, nothing changes. The placement's and the knobs' hazards are in `parity/HAZARDS.md` ("Placement and the parity knobs"). The dumps' CONF records showed three defaults of `PrintConfig.cpp` written as `float` literals, which `src/config.rs` keeps as the C++ has them (`FLOAT_LITERAL_DEFAULTS`).
- Orca's log (`src/log.rs`), set up at the start of `main` as `cli/main.cpp` sets it up: the records the crates log through orca-mesh's `log` (Orca's `BOOST_LOG_TRIVIAL`) at or above the level of `SKETCH_ORCA_LOG_LEVEL` (0 fatal, 1 error, the default, up to 5 trace) go to stderr as `[<severity>] <message>`, a line each.
- The decline (`src/decline.rs`): a job is checked against the families `parity/parity.json` certifies where it reaches a step this program does not do. The families it reaches are its command's (an info job's are model-load and info; a layers or slice job's are model-load, placement, slice-mesh, the internal concentric infill and every step `process()` runs whatever the settings, the tool ordering among them, then `layers` for layers and the G-code export and its processor for slice) and, for a layers or slice job, `multi-filament` with more than one filament, `painted-facets` when its model has support, seam, colour or fuzzy-skin painting (`decline::placed`, from the model as orca-model read it), and those its settings turn on: the wall generator, each surface's infill pattern, supports (`enable_support`, or `enforce_support_layers` above zero) or else `support-check` (an `enforce_support_layers` that does not read as a number gives both), raft, ironing, fuzzy skin, the prime tower (Orca's `has_wipe_tower`: with more than one filament, smooth timelapse, or clumping detection with an exclusion area of more than two points, counted as Orca's reader splits them), Z contouring, printing object by object (`print-by-object`) and multiline infill (`fill-multiline`, `fill_multiline` above 1 where there is sparse infill), read as the corpus reads them (`scripts/lib/parity/corpus.ts` `familiesFor`: the job's overrides, then its flattened process, machine and filament presets, then Orca's defaults from orca-config), and again for each object's overrides and each height range's. Its presets add `preset-conditions` where Orca works a compatibility condition out (`decline::preset_families`, as corpus.ts's `presetFamilies` finds it). Presets it cannot read leave the settings unknown, and the job then reaches every family a setting can turn on. A layers or slice job is declined once its objects are placed (and dumped, with the dump knob), as slicing is not ported: it gets result code `not-ported`, exit -8 and `missing`, the families it reaches past the front-objects boundary that are not done, in parity.json's order (`protocol/examples/result-not-ported.json`, a slice with Orca's default settings; a layers job's, every family of `process()` it reaches and `layers`, as corpus.ts gives them before its domain-A cut), before any output is written; the families before the boundary that this program does (`preset-conditions`, `model-load`, `placement`) are behind it by then, certified or not, so it names none of them (`decline::placed`). A job declined before the boundary names each family it reaches that this program does not do (one not in `decline::PORTED`, or not certified): one that orients its objects, naming `orient` too (in parity.json's order once parity.json lists it, after the others until then), and one whose compatibility condition the parser does not take. The work folder and its `orca-data` folder are made by then, as the C++ makes them, and so is a 3MF's backup folder. An info job is answered whole; both its families, model-load and info, are certified (2026-11-12), as is placement. parity.json is read at build time (`include_str!`), so a change to it takes a build, and the staged copy a `stage` (`BUILDING.md`, "The chain for an engine version"). `parity certify` fails when a run of a corpus job, example or refusal that reaches an uncertified family is not declined naming it. A declined run passes no family, and a run declined although the C++ run ended within what this program is to do itself (`endedWithinRust` of `scripts/lib/smoke.ts`: no stage past the job, the presets, the model and the placement) is wrong in itself; a layers or slice job the C++ refuses in placement is refused here as the C++ refuses it (`tests/place.rs`).
- A crash (`src/crash.rs`): an unhandled exception, an `abort` or a panic writes the `internal-error` result the C++ writes ("the engine crashed (<what>) during '<stage>', in Orca's code"), and the process ends with -1; no system crash dialog is shown. `SKETCH_ORCA_TEST_CRASH=<stage>` crashes with an access violation when the run reaches that stage, `<stage>:abort` with an abort, as in the C++ program, for the stages this program reaches (`job`, `presets`, `model`, `orient` for a job that orients its objects, and `arrange` for a layers or slice job that arranges them); `<stage>:panic` (this program only) with a panic; the point `decline` (this program only) is just before a decline is written, and its result names the stage the run declines in (`presets`, `model`, `orient`, or for a layers or slice job declined once its objects are placed `arrange`, or `model` when it does not arrange them).

On Windows stdout and stderr end their lines with a carriage return and a line feed, as the C++ program's text-mode streams do; files are written as bytes.

The modules: `main.rs` (the command line), `common.rs` (the failures and their exit codes, `cli/common.hpp`), `files.rs` (reading files, and writing them whole through `<file>.tmp`), `paths.rs`, `job.rs`, `result.rs` (results, progress, the run's files and `run_job`), `run.rs` (the work after the job is read, in `cli/run.cpp`'s order: the folders, the presets stage, the model stage, the orient decline, the info answer, the placement, the dump, the decline), `presets.rs` (the presets stage), `config.rs` (Orca's configuration: reading a value, the extruder variants, normalising, the defaults and Orca's check), `model.rs` (the model stage), `info.rs` (the info answer), `place.rs` (the placement), `oracle.rs` (the parity knobs and the front-objects dump), `log.rs` (Orca's log on stderr), `decline.rs`, `crash.rs`, `version.rs` and `config_def.rs`.

`tests/version.rs`, `tests/config_def.rs`, `tests/intake.rs`, `tests/info.rs`, `tests/place.rs`, `tests/decline.rs` and `tests/crash.rs` run the built program hidden (no console window) and compare what it writes with the front end's goldens and `protocol/examples/` (`tests/common/mod.rs` is what they share); `tests/intake.rs` fails when a refusal case of the corpus whose only family is `intake` has no test there. `tests/info.rs` holds three corpus info jobs (the 20 mm cube as a binary STL, Orca's 20mm_cube.obj and Orca's Büchse.3mf) and the lone triangle as an info job to the C++ program's result and progress bytes, a model path written with `/` (made preferred for the reader alone: the object's name and the reader's log line, not the result's message) and the model stage's refusals to the C++ program's results and log lines; their models, the C++ bytes (the corpus's goldens, or one run of the staged C++ program, 2026-11-11), the corpus's generic presets and the resources those presets read are in `tests/info/`. `tests/place.rs` holds the corpus's placement jobs and smoke.ts's placement refusals to one run of the staged C++ program with oracle patches 0001 to 0006 (2026-11-11): each refusal's result and progress file, and for each job the C++ program placed its front-objects dump byte for byte (the RUN record's FMA3 state this processor's) and a decline naming slicing alone; and the knobs, 24 refusals by their stderr and the RUN record under other knobs. Its jobs, models and the C++ bytes are in `tests/place/` (the jobs' paths written `<case>`, `<presets>` and `<resources>`, which `tests/common/mod.rs`'s `recorded_job` fills in). `tests/decline.rs` holds the printed lines of compatibility conditions that do not parse to the C++ program's (`tests/conditions/`, the same run). `tests/crash.rs` crashes at each stage the program reaches and at the point `decline`, for a job that orients its objects too. The modules hold their unit tests. `bun scripts/orca.ts parity certify` runs the program on the whole corpus (the repository's `README.md`).

Part of the Rust translation of sketch-orca (the workspace in the repository root; see the
repository's `README.md`, `BUILDING.md` and `CONTRIBUTING.md`). Licence: AGPL-3.0-only.

Build it with `bun run rs:build`; the program is `target/debug/sketch-orca-rs.exe` (`bun scripts/rust.ts build --release` builds `target/release/sketch-orca-rs.exe`).

Carries Boost.Filesystem code in `src/paths.rs` (Boost Software License 1.0; the repository's `NOTICE`). `src/config.rs`, `src/presets.rs`, `src/run.rs`, `src/model.rs`, `src/place.rs` and `src/log.rs` carry OrcaSlicer code (AGPL-3.0); each says which code from which file in its `Carries OrcaSlicer code` block.

## Rules

- The usage text, the exit codes and the result files follow `cli/` and `protocol/`; a difference is a bug in one of them.

## Dependencies

- `orca-crt`
- `orca-fmt`
- `orca-stl`
- `orca-tbb`
- `orca-probe`
- `orca-json`
- `orca-config`
- `orca-placeholder` (the presets' compatibility conditions)
- `orca-model` (the model stage: `read_from_file`, the model, its objects and parts)
- `orca-mesh` (the meshes, and `log`, whose records `src/log.rs` sends to stderr)
- `orca-eigen`, `orca-geom`, `orca-exact`, `orca-qhull`, `orca-zip`, `orca-xml` and `orca-arrange`: what orca-model stands on, named here from the model stage on (2026-11-11) for the steps that follow it; the placement (`src/place.rs`) calls orca-eigen, orca-geom and orca-arrange itself
- `sha2`
- `windows-sys`
