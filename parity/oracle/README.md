# The oracle

The oracle is the C++ engine with knobs: OrcaSlicer at the locked commit with `patches/` applied,
our front end (`cli/`), and then the patches in this folder's `patches/`. The parity harness checks
the Rust translation against it. Each knob makes one source of run-to-run variation fixed, or
makes the engine's state visible at a step boundary, so that a difference between the two programs
can be pinned on a cause.

**The oracle never ships.** It is built only by `bun scripts/orca.ts parity oracle`, into the work
folder (`<work>/oracle`), and no other command reads it: `build` and `stage` make the engine from
`patches/` alone, and the source bundle carries this repository's files, this folder among them,
as source, never the oracle's program. Parity work never changes `patches/`; everything the oracle
needs is here.

## The patches

`patches/NNNN-oracle-<name>.patch`, applied in order with `git apply` after `patches/`, to a clone
of the engine's checkout (`<work>/src`) at the locked commit, with `cli/` copied to
`sketch-orca/cli` (where the patches find the front end). Each starts with

```
sketch-orca oracle patch NNNN: <title>.
Modified for Sketch, <date>.

<what it changes and why>
---
<the diff>
```

The number in the header is the one in the file name, and the date is a real date
(`test/parity-oracle.test.ts` checks both, and `parity oracle` refuses a patch that breaks them).
Every patch acts only when its knob is set: with no knob set the oracle is the engine, which
`parity neutral` checks on every smoke case.

| Patch | Knob |
| --- | --- |
| `0001-oracle-clock.patch` | `SKETCH_ORCA_ORACLE_TIME` |
| `0002-oracle-seeds.patch` | `SKETCH_ORCA_ORACLE_SEED` |
| `0003-oracle-threads.patch` | `SKETCH_ORCA_ORACLE_THREADS` |
| `0004-oracle-fma3.patch` | `SKETCH_ORCA_ORACLE_FMA3` |
| `0005-oracle-dumps.patch` | `SKETCH_ORCA_ORACLE_DUMP` |
| `0006-oracle-front-objects.patch` | `SKETCH_ORCA_ORACLE_DUMP` (more in `front-objects-<n>.sop1`) |

## The knobs

A knob set to a value the oracle cannot read stops it before it does anything else: it prints
`sketch-orca-oracle: <what is wrong>` to stderr and exits with 78. A knob that is not set changes
nothing.

### `SKETCH_ORCA_ORACLE_TIME`: the clock

A time in whole seconds since 1970-01-01 00:00:00 UTC, from 315532800 (1980-01-01, the first time
a zip entry's DOS date holds) to 4102444799 (2099-12-31 23:59:59). The oracle reads it, as UTC,
wherever the engine reads the clock into what it writes: the G-code header's `generated by ... on`
line (`Utils::local_timestamp`, `GCode.cpp:2576`), the placeholder parser's `timestamp`, `year`,
`month`, `day`, `hour`, `minute` and `second` (`PlaceholderParser::update_timestamp`), the time
of every entry miniz writes into a 3MF (also where miniz would take a file's modification time:
the plate's G-code, written in the same run), the `srand(time(NULL))` of Lightning infill
(`Fill/Lightning/Generator.cpp:34`), FilamentGroup's time budget, the backup folder's name and the
import time a preset bundle records. The 3MF `CreationDate` and `ModificationDate` are written empty
by OrcaSlicer 2.4.2, so no clock reaches them.

Why: the clock reaches the outputs, so two runs of one job differ. `parity/masks.json` masks the
parts the engine writes every run; with the clock pinned, two runs are byte for byte the same, with
no mask at all.

### `SKETCH_ORCA_ORACLE_SEED`: the generators

A whole number from 0 to 4294967295. It seeds the two generators the engine seeds from entropy:
fuzzy skin's `std::mt19937` (`Feature/FuzzySkin/FuzzySkin.cpp`, otherwise `std::random_device`)
and the placeholder parser's `std::mt19937` (`GCode.cpp:2707`, otherwise the high-resolution
clock). `rand()` keeps the Universal CRT's default seed of 1 on every thread; no `srand` is added.
Lightning's `srand` follows the clock knob.

Why: fuzzy skin and `random()` in a G-code template write numbers drawn from those generators, so
without a fixed seed they differ on every run.

### `SKETCH_ORCA_ORACLE_THREADS`: the thread count

A whole number P from 1 to 256. The front end's `main` runs the whole run inside a
`tbb::task_arena` of concurrency P, while a `tbb::global_control(max_allowed_parallelism, 1)`, held
until the run ends, leaves TBB no worker thread. TBB then splits the work as for P threads, since
`this_task_arena::max_concurrency()` reports P to the code that asks (`TreeSupport3D.cpp:2385`,
`TreeModelVolumes.cpp`, the partitioners), and does all of it on the main thread, in one order, the
same on every run. `utils.cpp:196-204` is left as it is: its `disable_multi_threading` builds a
temporary `global_control`, which does nothing. `name_tbb_thread_pool_threads_set_locale`
(`Thread.cpp`), which `Print::process` calls, returns at once under this knob: there are no worker
threads to name, and its barrier would wait forever on one thread.

Why: where the engine's results depend on how TBB splits work or on the order threads finish,
they depend on the machine's core count and on timing. One order at a chosen P makes such a
difference reproducible; comparing P=1 with P=8 finds it (`parity neutral` (c), the T candidates).
Whether the arena really reports P is read from the oracle, not assumed: every dump's RUN record
gives what `max_concurrency()` returned (`parity/SOP1.md`), and `parity neutral` records it.

### `SKETCH_ORCA_ORACLE_FMA3`: the CRT's maths paths

`0` or `1`. With `0` the oracle calls `_set_FMA3_enable(0)` before anything else, from a static
initializer in the compiler's initialization segment (`#pragma init_seg(compiler)`,
`cli/oracle_fma3.cpp`), which runs after the CRT's own and before every other static initializer of
the program. The Universal CRT's x64 maths functions (`exp`, `log`, `pow`, `sin`, `cos` and the
rest) then take their SSE2 paths whatever the CPU. `1` is the CRT's own choice, as unset is. Only
x64 MSVC builds take `0`.

Why: the CRT picks FMA3 code paths at run time on CPUs that have them, and their results can differ
in the last bit from the SSE2 ones. With the paths fixed, the oracle's floating point is the same on
every machine, as the Rust translation's must be.

### `SKETCH_ORCA_ORACLE_DUMP`: the step boundaries

An existing folder. The oracle writes SOP1 files there (`parity/SOP1.md`) at step boundaries only,
never inside a step: after each print object step and each print step (from `set_done`,
`PrintBase.hpp`), and in the front end once the objects are placed and once the config is resolved
and applied. `Print` gets one friend, `OracleDumpAccess`, for the brims, the skirt's convex hull and
the wipe tower data. Patch 0006 (2026-11-07, no knob of its own) puts all the front end has into
`front-objects-<n>.sop1`: the front end's config at that point (`load_settings`' config with the
prime tower's place), the plates' custom G-code, and each object's height ranges, brim ears and
volumes' painting, so the Rust translation's presets, model loading and placement can be checked
at that boundary (`parity/SOP1.md`).

Why: an output that differs says where, not why. The dumps give the state at each boundary, so a
difference can be traced to the first step whose state differs.

## Building it

```
bun scripts/orca.ts parity oracle
```

It needs the engine's dependency build (`bun scripts/orca.ts build`), which it shares and never
rebuilds, and at least 40 GB free on the work folder's drive; see `BUILDING.md`. It writes:

```
oracle/src/      the clone with patches/, cli/ and these patches applied
oracle/build/    the Ninja build (the linker map sketch-orca.map beside sketch-orca.exe)
oracle/state/    what the clone and the build were made from
oracle/dist/     bin/sketch-orca-oracle.exe, bin/sketch-orca-oracle.map, the libraries it loads,
                 resources/ (profiles, info, flush) and oracle.json
```

## Checking it is neutral

```
bun scripts/orca.ts parity neutral
```

It runs every smoke case's jobs three ways and writes `<work>/parity/neutral.json`:

- (a) with no knob set, the oracle's outputs equal those of the engine staged from this checkout
  (`<work>/dist/engine`) after `parity/masks.json`;
- (b) with `SKETCH_ORCA_ORACLE_TIME` and `SKETCH_ORCA_ORACLE_SEED` set, two runs of the oracle are
  byte for byte the same, with no mask;
- (c) with `SKETCH_ORCA_ORACLE_THREADS=1` and `=8` (time and seed pinned, each run dumping), every
  run finishes, and each output or dump that differs between them is recorded as a T candidate.

It exits 1 when (a) or (b) fails, 0 when both pass; (c) is a record, not a gate.

## The probe program

`probe/` is a second C++ program built against the oracle's build tree, never shipped:

```
bun scripts/orca.ts parity probe [--check]
```

It compiles with the compile line of the oracle's `config_def.cpp` and links with the oracle's link
line (read from `oracle/build/build.ninja`), into `oracle/probe-build/`, so its maths, formatting,
sorting, hashing, random numbers and threading are the engine's own: the static UCRT, MSVC's STL,
oneTBB and libslic3r. It writes what they do as SOP1 files (`parity/SOP1.md`, "Probe files"):

| File | Source | What it records |
| --- | --- | --- |
| `crt.sop1` | `crt.cpp` | every maths function of the static UCRT that the oracle's linker map lists, on edge and swept inputs, with FMA3 on and off; MSVC's casts; `rand()` |
| `fmt.sop1` | `fmt.cpp` | `snprintf` formats, `std::to_chars`, iostream output, `to_string`, and the parsers (`strtod`, `strtof`, `std::stod`, `std::stof`, `from_chars`; not yet `istream >>`, see `../HAZARDS.md`) |
| `stl.sop1` | `stl.cpp` | sorts, stable sorts, `nth_element`, partial sorts, merges, heaps and searches on patterned inputs; `std::hash`; unordered containers' iteration order; random engines and distributions; `shuffle` |
| `tbb.sop1` | `tbb.cpp` | how oneTBB splits `parallel_for` and `parallel_reduce` ranges with each partitioner, for P from 1 to 64 |
| `configdef.json` | `configdef.cpp` | Orca's whole `print_config_def`, its option lists, legacy keys and `handle_legacy` |

`parity/probes/` keeps a subset under 8 MB; the full set stays in `<work>/parity/probes`. The crates'
`tests/probes.rs` replay them (`SKETCH_ORCA_PROBES_DEEP` for the full set; `crates/orca-probe/README.md`). `probe/recorded/` holds the smaller
programs whose outputs the crates' own unit tests carry as constants (`probe/recorded/README.md`).
